# WX-439 — Manual test procedure

**Ticket:** WX-439 — enable the Grafana `pinNavItems` feature toggle so dashboards are reachable from
the left nav.
**Release:** none — no version bump. The change is one environment variable in
`observability/docker-compose.yml`; it ships in no service binary, so `Directory.Build.props` and
`VERSIONS.md` are untouched (WORKFLOW §5).
**Component:** the `grafana` container of the observability stack. Verified interactively — the effect
is a browser UI change, so there is nothing for the unit suite to assert.
**Script:** `docs/test-procedures/WX-439-verify.sh` covers steps 1–3. Steps 4–6 are browser UI and
stay manual.

**What changed:** one line in the `grafana` service's `environment:` block —

```yaml
      - GF_FEATURE_TOGGLES_ENABLE=pinNavItems
```

With the toggle on, Grafana's left nav gains a **Starred** section and a **Bookmarks** section, so a
starred or bookmarked dashboard is one click away instead of requiring Dashboards → Browse every time.

## 🔴 READ THIS BEFORE STEP 1 — what this procedure can and cannot prove

**The runtime effect has been live on the production machine since 2026-08-14** as an uncommitted
working-tree edit. So steps 4–6 below, run on their own, **cannot distinguish "the merged change
works" from "it was already working before the merge"** — they would pass either way.

**And a container fingerprint alone does not close that gap either.** `docker compose` always reads
the **working-tree** file, never a committed blob, so "the container is configured from the committed
change" is not directly observable. It follows from two checks, and needs both:

- **(a)** the working-tree file is identical to the blob at `origin/master` — script checks 3, 4, 5;
- **(b)** the running container's environment matches what that file specifies — script check 6.

**Measured, in the pre-merge state, and this is the negative control for the whole procedure:** run
against this branch before the merge, the script reported **check 6 PASS while checks 3 and 4 FAIL** —
the container carried the toggle while the toggle was on no branch at all. That is the state the
ticket exists to end, and it is why (b) alone was never a discriminator.

**The before/after that establishes the toggle is what gates the nav is cited, not re-run.** It was
observed on 2026-08-14 and is recorded in **WX-439's own description**: before the toggle the nav had
no route to the dashboards and neither starring nor bookmarking produced one; after the toggle, both
did. Re-running it means deliberately breaking production's Grafana nav to re-prove a known result.

**So the verdict turns on steps 1–3.** Steps 4–6 confirm the merge did not disturb a working state.

**Setup:** run after the PR is merged to `master` and the working tree is reconciled (AC-2). All
commands from the repo root; the Docker commands need Docker Desktop running.

Read one step at a time; report the result of each. Note any failure and continue; the failed-step
list is the deliverable.

## Steps

1. **Recreate Grafana from the current tree** — this must come first, so that step 3 inspects a
   container built from the file step 2 is about to check:

   ```bash
   docker inspect -f '{{.Id}}' observability-grafana-1          # note this value
   cd observability && docker compose up -d --force-recreate grafana && cd ..
   docker inspect -f '{{.Id}}' observability-grafana-1          # must DIFFER from the above
   ```

   *Expect:* the two IDs **differ**. **`--force-recreate` is required and is not belt-and-braces:**
   plain `docker compose up -d grafana` is a **no-op** whenever the compose file has not changed since
   the container was built — measured, `--dry-run` prints `Running` for the plain form and `Recreated`
   only with the flag. Since the committed file is byte-identical to the working-tree edit the current
   container was already built from, the plain form would change nothing and step 3 would fingerprint
   a container created on 2026-08-14.
   The `grafana-data` named volume is not touched by `--force-recreate`, so stars survive; the
   dashboards are baked into the image (WX-278) and survive too. Only Grafana is recreated.

2. **Run the verification script:**

   ```bash
   bash WxServices/docs/test-procedures/WX-439-verify.sh
   ```

   *Expect:* `PASS` and rc=0, with all six checks passing. It asserts, in order: the path is really
   tracked; `origin` is fetched; HEAD is `master` and level with `origin/master`; the committed blob
   carries the toggle exactly once (**AC-1**); the working tree is clean for that file (**AC-2**); and
   the recreated container carries the toggle. On `FAIL` the failing check names what it expected.

3. **If the script cannot run** (no Docker, or rc=2), the three git assertions by hand:

   ```bash
   git fetch origin
   git ls-files --error-unmatch observability/docker-compose.yml   # rc=0; rc=1 means a typo'd path
   git rev-parse --abbrev-ref HEAD                                 # expect: master
   git rev-parse HEAD; git rev-parse origin/master                 # expect: identical
   git show origin/master:observability/docker-compose.yml | grep -c pinNavItems   # expect: 1
   git status --porcelain -- observability/docker-compose.yml      # expect: no output
   ```

   ⚠️ **Three of those need their traps stated, because each has a silent failure mode:**
   `git fetch` is not optional — `origin/master` is a *local* ref, and without a fetch, step 2 reports
   a spurious AC-1 failure immediately after a browser merge. `git status --porcelain` on a **mistyped
   path** prints nothing and exits 0, which is byte-identical to its own pass condition — that is why
   `git ls-files --error-unmatch` runs first, as the only form here that discriminates a real path
   from a typo. And a clean `git status` proves the tree matches **HEAD**, not `origin/master`: it is
   equally clean while parked on the feature branch, so the branch and revision checks are what make
   it mean **AC-2**.

4. Open Grafana at `http://localhost:3000` and **refresh the browser** (Ctrl+F5). Look at the left nav.

   *Expect:* a **Starred** section and/or a **Bookmarks** section is present, listing the dashboards
   that were starred or bookmarked. **AC-4.**
   ⚠️ The nav does not repopulate on its own after a container recreate — the refresh is required. A
   nav with no such section on a stale page is not a failure until it has been refreshed.

5. If no dashboard is currently starred, star one (the ☆ beside a dashboard's title) and refresh.

   *Expect:* it appears under **Starred** in the left nav. Starring alone is sufficient — bookmarking
   is a second route to the same place, not a prerequisite.

6. Go to **Dashboards → Browse**.

   *Expect:* all four provisioned dashboards are listed **by title** — **WxMonitor**, **WxParser**,
   **WxReport**, **WxVis** — and each **opens**, resolving its UID (`wxmonitor-v1`, `wxparser-v1`,
   `wxreport-v1`, `wxvis-v1`) rather than showing "Dashboard not found". **AC-5, the negative control
   against a fix that over-reaches:** the toggle must add a route without disturbing provisioning.
   ⚠️ Browse lists **titles**; the UIDs appear only in the URL. They are named here because the
   WX-278 regression this step guards against presented as an *"Invalid dashboard UID"* 404 — so the
   title check and the opens-without-404 check are both load-bearing.
