# WX-457 — verifying a comments-only trim

**Reusable.** Nothing below is specific to `ForecastReconciler.cs` except the defaults.
`ReportWorker.cs` (369 narrative comment lines) is the intended next subject.

## What this proves, and why reading the diff is not enough

Three reviewers read the WX-457 diff — a context-free reader, a sibling instance, and Paul — and
between them found twelve defects. **Four of the mechanical ones were found only by these checks**,
and one of those was created *by a repair* two hours after every reviewer's pass, so no amount of
reading could have caught it.

🔑 **Reading finds MEANING. These checks find MECHANISM. A trim needs both, and they do not
substitute for each other.**

## Run it

    cd WxServices
    ./docs/test-procedures/WX-457-verify.sh                    # defaults to this ticket's file
    ./docs/test-procedures/WX-457-verify.sh --file PATH --base REV --head REV
    ./docs/test-procedures/WX-457-verify.sh --selftest         # prove the checks can fail

Both revisions are read **from git**, never from a working copy or a scratch file — a verification
that depends on an unversioned artifact cannot be re-run by anyone else.

## What it checks

| # | Check | Catches |
|---|---|---|
| **AC-1** | Strip comments from both revisions (respecting `"…"`, `@"…"`, `'…'`) and compare the surviving code | A trim that silently changed code |
| **control** | Plant a real code change and confirm AC-1 **fails** | AC-1 having become decoration |
| **1** | Comment blocks opening with a lowercase word | A stripped leading `WX-nnn:` stamp left the sentence headless — 0 → 36 on the first pass |
| **2** | Doubled words, including across a re-flowed line join | Two comment lines merged into one |
| **3** | A comment block ending on `—`, `:` or `(` | Punctuation that belonged to the sentence went with the deleted reference |
| **4** | `///` text changed *(informational)* | A claim that XML docs were untouched |
| **baseline** | Guards 1–3 against the **pre-trim** file | The guards flagging pre-existing noise rather than new damage |

## Two things that must not be simplified away

🔴 **The positive control plants CODE, not a comment.** An earlier version inserted `/*x*/` and
AC-1 correctly ignored it — so the control reported failure while the check was working perfectly.
**A control that plants the wrong KIND of change measures nothing**, and it fails in the direction
that makes you distrust a good check. The mutation now edits an integer literal and **aborts loudly
if it cannot apply**, because a mutation that silently fails to apply looks exactly like a kill.

🔴 **The baseline run is not decoration.** Guards 1–3 must read clean against the *pre-trim* file.
If they do not, they are reporting the file's existing habits rather than the trim's damage, and
every number above them is meaningless.

⚠️ **Guard 4 is reported, not scored.** Doc text legitimately changes when a trim repairs a doc
that had become false — which is what happened here, and why `///` lines went *up*. It refutes only
a claim of "docs untouched".

## Expected result

    AC-1 PASS ... code byte-identical
    positive control ... planted code change detected
    guards ... 0 / 0 / 0
    baseline ... 0 / 0 / 0
    ====> PASS

A `FAIL` on guards 1–3 with a clean baseline means the trim introduced the defect. A `FAIL` on the
**control** means the verification itself is broken — fix that before believing any other line.

## Scope

This procedure does **not** check whether a comment is *true*. That is what a reviewer is for, and
it is where the serious findings were: an inverted meaning, a rule asserting more than the code
enforces, a surviving doc left false by a deleted qualifier. **Never read a green run here as
"the trim is good" — only as "the trim broke nothing mechanical."**
