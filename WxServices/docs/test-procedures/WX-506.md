# WX-506 — Functional test procedure (production §13 watch)

**Ticket:** WX-506 (Bug under Epic WX-153). The "Why this update" band is now written by a second model
call, after the change detector runs, from the computed changes alone. Before, the reconciliation call
wrote it and could report its GFS-only draft's value as the prior forecast's: send 9341 claimed Tuesday
afternoon rain was new when it was not, and called Wednesday's real change "remains".

It also makes the significance gate and the change detector share one set of rules: a day's temperature and wind
compare the forecast last sent (whole day) with the new one (hours already past kept as sent), and What's Changed
names a precipitation or severe change only where one of the gate's criteria fires.

v1.61.6 closes a gap the v1.61.5 watch did not look for: an unscheduled update sent with no band. The gate
reads the provisional forecast and the band comes from the reconciled one, so when reconciliation dropped the
change the gate saw, the update went out with nothing new to say (14 of 79 unscheduled updates from
2026-09-15 to 2026-09-25). An unscheduled update whose reconciled report has no computed change is now
withheld, logged as `WX-506 suppressed`, unless a severe hazard appears on a baseline reset.

v1.61.7 stops that rule paying for the same answer over and over. The gate reads the model's forecast and
Claude may not adopt its change, so a withheld update left everything as it was and the next arrival asked
Claude the same question again: Austin, TX fired `precip-remove@T1(09-30 11Z)` on 18 consecutive arrivals on
2026-09-29/30, each a full reconcile that was then withheld (ticket comments 16508, 16510). A withheld update,
or Claude's answer that an arrival is not news, now records the criteria its gate fired, the evidence Claude
weighed and the prior the gate measured against. Within 6 hours, a cycle whose gate fires only those criteria, against
the same prior, with the same TAF and GFS run and a METAR unchanged in station, present weather, wind band and visibility
band, skips the Claude call, logged as `WX-506 repeat skipped`. A new criterion, a severe onset, a new prior, new
guidance, new observed weather or the 6 hours running out asks Claude again (logged at DEBUG as `WX-506 rejected-gate
record not applied (<reason>)`), and a delivered weather report clears the record.

v1.61.8 stops a TAF amendment on its own from reopening the question. On 2026-10-01, in a slow, unsettled
pattern, KIAH's TAF was amended six times in six hours; all 7 re-asks that a new TAF alone caused got the same
answer, while all 3 caused by a new GFS run sent (ticket comment 16564). The skip now ignores the TAF's issuance
time: the gate merges the TAF into its forecast, so an amendment that matters fires a criterion not on record or
moves the prior, and Claude is asked. A new GFS run still always asks again, logged as `NewGfsRun` (`NewGuidance`
in logs before v1.61.8).

**Release under test:** v1.61.8 · **Component:** `WxReport.Svc` (the reconciler, the change detector, the
significance gate, the unscheduled-send backstop and the repeat skip).

## Why this is a production watch

The fix changes what the model is given, not a deterministic rule, so the evidence is the bands that
actually ship. The unit tests cover the deterministic half: the band call runs only when a band shows,
its input holds only the computed changes, prose checks apply to it, every failure falls back to
the deterministic band, the send decision withholds an unscheduled update with no computed change, and the
renderer shows the band whenever the report carries a change. No unit test covers the send path passing the
report's change count to that decision; B4 below is what checks it. The reverse gap: B4 counts every send on
a baseline reset as by design, so it cannot tell whether a reset exemption let through only severe onsets;
the unit tests check that scoping. The pre-deploy replay of send 9341 (WX-506 comment 15931) is one sample.

## The classes

Judged per locality cycle, against that cycle's own computed changes (the `changes` in its structured
report), in the locality's local time.

| Class | A defect is |
|---|---|
| **B1** — a fabricated change | the band names a change, a prior value or a window that its computed changes do not contain: an unchanged window called new or upgraded, a real change called unchanged, a prior value stated wrongly, or a change on the wrong day or day-part. |
| **B2** — a fallback | a cycle with computed changes whose band is empty in some language, so recipients saw the deterministic fallback line instead. Not a correctness defect; its rate is recorded and bounded in the verdict. |
| **B3** — a wording slip | a band that names only real changes but words one inexactly (e.g. extends a day-part the change does not cover). Recorded, not part of the verdict. |
| **B5** — a repeated rejection | an unscheduled cycle on which Claude was asked what it had already answered: an earlier cycle for the same locality was withheld (no computed change, or redundant) or judged not news, and a later one less than 6 hours apart ended the same way although its gate fired only criteria from the earlier one, with no weather report delivered in between and no logged reason to ask again. Found from the service log by `WX-506-repeats.py` (step 6c). |
| **B4** — an update with no band | an unscheduled update sent with no band at all. Found from the service log, not the dump (step 6). Two sends omit the band by design and are counted separately, not as B4: a narrative-less hazard report (WX-148), and a severe hazard appearing on a baseline reset (the prior dropped after a schema bump). |

## Files beside this procedure

* `WX-504-dump.ps1` — writes every sent `CommittedSend` since `-Since` as UTF-8 JSON lines. It
  **reads the production database**.
* `WX-506-screen.py` — groups the dump into locality cycles and prints each cycle's computed changes
  beside its bands, the command that shows the facts each band was written from, band-call log
  counts, and each bandless unscheduled update it finds in the logs. **A pairing aid, not a verdict.**
  `--selftest` must pass.
* `WX-506-repeats.py` — reads the service logs and prints each repeated rejection (B5), the counts of
  withheld updates and of skipped repeats, and Claude calls per day. `--selftest` must pass.
* `WxReport.Tools.TranslationQa --replay-band --facts-only` — prints the facts a band call receives for a
  stored pair of snapshots: each change's window and its prior → now values. It makes no model call and
  **reads the production database**. The band's prior values exist only here; the dump does not carry them.

## Procedure

1. **Confirm the deploy.** Run
   `bash /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/deploy-info.sh --version 1.61.8 WxReportSvc`.
   *Expect:* one line, `<timestamp><TAB><commit>`. The timestamp is the window start, `SINCE`.

2. **Baseline smoke.** Confirm that `WxReport.Svc` came up cleanly: the container is healthy, reports
   continue, and `wxreport-svc.log` has no new ERRORs beyond the pre-deploy background.
   *Expect:* healthy.

3. **Wait for the window:** at least **7 days** after `SINCE`, and at least **10** locality cycles with a
   band (step 6 counts them). With fewer, wait and repeat from step 4; record no verdict.

4. **Dump the corpus.** Paul runs this line in the terminal, with `!` prefixed and `DUMP_FROM` filled in as
   `SINCE` minus 2 days — the earlier rows supply each early cycle's prior snapshot:

       powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$(wslpath -w /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-504-dump.ps1)" -Since 'DUMP_FROM' -OutPath "$(wslpath -w /tmp)\wx506-corpus.jsonl"

   *Expect:* `rows=N`, where N > 0.

5. **Self-test the screen.**

       python3 /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-506-screen.py --selftest

   *Expect:* every line `ok`, and a final line `33/33 as expected`. Any `FAIL` means the screen is
   broken; stop.

6. **Screen the corpus.**

       python3 /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-506-screen.py /tmp/wx506-corpus.jsonl --since 'SINCE' $(for f in /mnt/c/HarderWare/Logs/wxreport-svc.log*; do printf -- '--log %s ' "$f"; done)

   *Expect:* a first line `cycles_with_changes=C  with_band=B  fallback_or_no_band=F`, one block per
   cycle, a line `log: window_start=…  band_written=W  band_fallback=X  earliest=…  coverage=…`, and a last
   line `updates: sent=U  bandless=K  by_design_without_band=H`, followed by one `B4 bandless update:` line
   per bandless update.
   * **Exposure.** `B` must be at least 10. If not, go back to step 3.
   * **Cross-check, only when `coverage=complete`.** Every cycle with changes is a band call — unscheduled
     updates, and scheduled or diagnostic reports carrying a near-term severe onset — so `W + X` should be
     close to `C`. A large shortfall means cycles are not reaching the band call, which is itself a finding.
     `W + X` may exceed `C` by the number of diagnostic reports carrying a near-term severe onset: those
     make a band call and log a fingerprint, but the screen leaves diagnostic sends out of `C`.
     With `coverage=INCOMPLETE`, the logs have rotated past `SINCE`: the counts are partial and the
     cross-check is skipped, not passed.
   * **B4.** `K` must be 0. Each `B4 bandless update:` line names the locality and when its cycle began; read
     that stretch of the log and record what happened. `U − H` must be above 0, or no banded unscheduled
     update was tested. Like the cross-check, B4 is assessed only when `coverage=complete`; with `INCOMPLETE`, pass the
     older rotated logs or record no verdict.

6b. **Record the gate's decisions — context, not a verdict.** Late-day cooling and calming no longer prompt an
    unscheduled update, so fewer are expected. Count the gate's passes and suppressions for the 7 days after
    `SINCE` and the 7 days before it:

        for f in /mnt/c/HarderWare/Logs/wxreport-svc.log*; do cat "$f"; done | grep 'WX-114 significance gate' | awk '{print $1, ($0 ~ /passed/ ? "passed" : ($0 ~ /WOULD suppress/ ? "would-suppress" : ($0 ~ /suppressed/ ? "suppressed" : "other")))}' | sort | uniq -c

    Also count the updates the backstop withheld: `for f in /mnt/c/HarderWare/Logs/wxreport-svc.log*; do cat "$f"; done | grep -c 'WX-506 suppressed'`.

    *Expect:* a count per date and outcome, and a count of withheld updates. Record all of them in the ticket comment. If the logs do not
    reach back 7 days before `SINCE`, record the week you have and say so. A fall in passes is expected; a rise, or
    a day with no passes at all, is a finding to look at.

6c. **Repeated rejections (B5) and the cost they drove.**

        python3 /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-506-repeats.py --selftest
        python3 /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-506-repeats.py --since 'SINCE' $(for f in $(ls -r /mnt/c/HarderWare/Logs/wxreport-svc.log*); do printf -- '--log %s ' "$f"; done)

    The self-test must end `23/23 as expected`. The second command reads the logs oldest first and prints
    `repeats: withheld=W  repeat_skipped=R  B5=N`, one `B5 …` line per repeated rejection, and one `calls <date> <n>`
    line per day.
    *Expect:* `N` = 0. Record `W`, `R` and the calls per day in the ticket comment, beside the same count for the
    week before `SINCE`, taken with `--since` set 7 days earlier (the same command run over the log from
    2026-09-25 22:44Z to 2026-09-30 found `B5=37` among 46 withheld updates and not-news answers, so the screen does
    find them; that log predates the re-ask reasons, so some of those 37 had new guidance and v1.61.7 would rightly
    have asked again). Calls per
    day should return to their pre-2026-09-29 range on comparable weather: 7 to 29, typically 8 to 15.

7. **Judge every band by hand** against its facts. For each cycle with a band, run its `facts:` line from
   PowerShell in `C:\Code\HarderWare\WxServices`.
   *Expect:* exit 0, a first line `now: <UTC instant>`, and a `computed_changes` block. A cycle printing `prior not in corpus`
   needs an earlier `DUMP_FROM`. The replay takes the cycle instant from the final snapshot's generation time, a
   little after the cycle's changes were computed. When a 6-hour block boundary falls between the two, a block can
   count as elapsed in the replay and not in the cycle, which changes both the change set and the day figures.
   **Before judging, check the replay against the screen:** the same changes in the same order, and each temperature
   or wind change's `now` figures equal to the stored `now:` quantities printed above it. If either differs, do not
   judge that band: record the cycle as **not judgeable (replay mismatch)**, which counts neither as B1 nor as clean.
   A not-judgeable cycle does not count toward the 10 banded cycles.
   Judge the band against the printed facts **and** the changes above it. For each cycle record: snapshot
   id, send date, the band, and **B1**, **B3** or "clean". For a B1, name the claim and the fact (or
   absence of one) it contradicts.
   *Expect:* a written disposition for every cycle with a band.

8. **Cross-check one B1 (if any) against the rendered email** — the dump's `EmailBody` for a send of
   that snapshot — to confirm the band reached recipients in that form.

## Verdict

* **PASS** — `B` ≥ 10, every band judged, **no confirmed B1**, the fallback rate `F ÷ C` is at
  most 25%, `coverage=complete` with `U − H` > 0 and **`K` = 0 (no B4)**, and **`N` = 0 (no B5)**. Record
  `PASS yyyy-mm-dd @ v1.61.8` in **Test Result**, with the B2 rate, the B3 count, `H`, the withheld-update and
  skipped-repeat counts and the calls per day in a ticket comment.
* **FAIL** — any confirmed B1, any B4, any B5, or a fallback rate above 25% (above that, at least one update in
  four loses the written band). Record `FAIL yyyy-mm-dd @ v1.61.8` and the offending bands, updates or rate.
