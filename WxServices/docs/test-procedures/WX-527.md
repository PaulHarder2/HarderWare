# WX-527 — Functional test procedure (production §13 watch, waits for a real outage)

**Ticket:** WX-527 (Bug under Epic WX-270). From 2026-09-06 09:09Z to about 2026-09-07 05:00Z every SMTP
send failed ("Network is unreachable") while Claude stayed reachable. Nothing was delivered, so nothing
advanced, and every cycle generated the scheduled report again through Claude: 265 reconciles on 09-06,
about $35, 28% of the LLM bill for 2026-08-14 to 2026-10-01.

v1.61.9 re-sends instead. A failed send leaves its `CommittedSend` rows unsent with the rendered email; each
row now also records `ReportKind` and `InputIdentity` (the evidence it was built from). At the start of each
locality's cycle, the latest-written reconciled report batch (any later delivery supersedes it) younger
than 3 hours with unsent rows is re-sent to the recipients still owed, with no Claude call, unless Paul's rules make it stale:

1. a severe block in it has come within the 36-hour hazard horizon since it was generated;
2. it is 3 hours old (it then simply stops being pending);
3. a day-part boundary (00/06/12/18 local) has passed: always for a scheduled report; for an unscheduled
   update, when one of its changes lies in the day-part that ended;
4. the evidence has moved on in substance: a new GFS run, a METAR changed in station, present weather, wind
   band or visibility band, or a TAF different in substance.

A stale report falls through to the normal cycle. When the report reached nobody (an outage), a re-send that
fails again ends the cycle without a reconcile; after a partial delivery the re-send to the members missed is
best-effort, at most hourly, and the normal cycle continues.

**Not covered** (and not a B1 below): a locality's first cycle, whose members are all unserved and get
welcomes only, and a degraded hazard report. Neither leaves a re-sendable report, so an outage still
reconciles them each cycle.

**Release under test:** v1.61.9 · **Component:** `WxReport.Svc` (the pending-delivery re-send) and the
`CommittedSends` schema (v4).

## Why this waits for an outage

The behaviour only runs when a send fails. Paul chose (2026-10-01) to verify it on the next real outage
rather than break SMTP on purpose, so this ticket may stay **In Test** for a long time. Steps 1–2 run at
deploy; steps 3–6 run when step 3 finds an outage.

## Procedure

Every path is relative to `WxServices/`. Logs are `C:\HarderWare\Logs\wxreport-svc.log*` (WSL:
`/mnt/c/HarderWare/Logs/`), UTC.

1. **Confirm the deploy.** Run
   `bash /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/deploy-info.sh --version 1.61.9 WxReportSvc`.
   *Expect:* one line, `<timestamp><TAB><commit>`. The timestamp is `SINCE`.

2. **Baseline smoke and the new columns (the fingerprint).** The container is healthy, reports continue, and
   the log since `SINCE` has no new ERROR beyond the pre-deploy background. Then, from PowerShell:

       & 'C:\Program Files\Microsoft SQL Server\Client SDK\ODBC\170\Tools\Binn\SQLCMD.EXE' -S '.\SQLEXPRESS' -E -C -d WeatherData -Q "SELECT COUNT(*) AS rows, SUM(CASE WHEN ReportKind IS NULL OR InputIdentity IS NULL THEN 1 ELSE 0 END) AS missing, MAX(SchemaVersion) AS v FROM CommittedSends WHERE CreatedAtUtc >= 'SINCE' AND IsDiagnostic = 0 AND StructuredReport IS NOT NULL"

   *Expect,* once at least one weather report has gone out after `SINCE`: `rows` > 0, `missing` = 0, `v` = 4.
   The old behaviour is gone only when every new weather row carries both values.

3. **Find an outage.** Periodically (the resume queue is the reminder):

       tr -d '\000' < /mnt/c/HarderWare/Logs/wxreport-svc.log | awk -v s='SINCE' '($1" "$2) >= s' | grep -c 'Failed to send email'

   (Use the rotated `.log.N` files too if the window spans them.) *Expect:* 0 most of the time, and then
   record nothing. A count above 0 is an outage, or a single recipient's failure: go to step 4 with that
   window.

4. **Read the outage, locality by locality.** For the window, from the first `Failed to send email` to an
   hour after the last:

       grep -F "locality '<name>'" <log window> | grep -E 'Claude tokens|WX-527|report sent|generating'

   (Every one of these lines names the locality, but not always first: a delivery reads
   `<recipient> <email> (<name>): report sent (locality '<name>' (Id=…)).`)

   *Expect,* for each failed report that reached **nobody** (no `report sent` line for it):
   * one Claude call that generated it (`Claude tokens […/reconciled]`);
   * then, each later cycle, `WX-527 re-sending the pending …` with **no** `Claude tokens` line, until either
     it is delivered or `WX-527 pending … not re-sent (<reason>)` is logged. That line is written once per
     report and reason, so later cycles in which the report is still stale log nothing, and their Claude
     calls are expected;
   * a `Claude tokens` line only **after** a `not re-sent` line for that report, or once the report is 3
     hours old.

   A `Claude tokens […/reconciled]` line for such a locality while its report is under 3 hours old, with no
   `not re-sent` line for that report earlier in the window, is a **B1** (the loop this ticket exists to
   stop). A report that reached **some** members is never a B1 case: its re-send is best-effort, at most
   hourly (`… (best effort; the normal cycle continues)`; the cycles between log nothing), and the normal
   cycle runs every cycle.

5. **Check each `not re-sent (<reason>)` line against the rules.**
   * `DayPartCrossed`: the generation time and this cycle are in different local day-parts; for an
     unscheduled update, a change window touches the day-part that ended (read `changes[].window` in the row's
     `StructuredReport`).
   * `NewGfsRun` / `NewWeather` / `NewTaf`: the GFS run, the METAR's station/present weather/wind band/
     visibility band, or the TAF's substance changed since the row's `InputIdentity`. A `NewTaf` should sit
     next to a `WX-527 pending report TAF comparison different` DEBUG line.
   * `SevereOnset`: a severe block in the report's snapshot reached 36 hours ahead after generation.

   A reason the evidence does not bear out is a **B2** (regenerating without cause).

6. **Check delivery and duplicates.** After mail returns, for each failed report:

       SELECT RecipientId, ForecastSnapshotId, CreatedAtUtc, SentAtUtc, ReportKind FROM CommittedSends WHERE CreatedAtUtc >= '<outage start>' AND IsDiagnostic = 0 ORDER BY ForecastSnapshotId, RecipientId

   *Expect:* each recipient's row on the last pending report has `SentAtUtc` set (or that report went
   stale and a newer one reached them). A recipient with two sent rows of one batch (same snapshot,
   `ReportKind` and `InputIdentity`) is a **B4**, a duplicate. Two sent rows for one snapshot from different
   batches are not: a WX-182 cached re-send legitimately sends an older snapshot again (its `ReasoningTrace`
   begins `WX-182 cached re-send`). A recipient who missed a report that was neither re-sent nor
   regenerated is a **B3**.

       SELECT RecipientId, ForecastSnapshotId, ReportKind, InputIdentity, COUNT(*) FROM CommittedSends WHERE CreatedAtUtc >= '<outage start>' AND SentAtUtc IS NOT NULL AND IsDiagnostic = 0 GROUP BY RecipientId, ForecastSnapshotId, ReportKind, InputIdentity HAVING COUNT(*) > 1

   *Expect:* no rows.

## Verdict

* **PASS** — an outage observed, with no B1, B2, B3 or B4. Record `PASS yyyy-mm-dd @ v1.61.9` in **Test
  Result**, with the outage window, the generations, re-sends and regenerations per locality, and the Claude
  calls against what the old behaviour would have made (about one per cycle).
* **FAIL** — any B1, B2, B3 or B4. Record `FAIL yyyy-mm-dd @ v1.61.9` and the offending lines.
* **WAIT** — no outage yet. Record nothing.
