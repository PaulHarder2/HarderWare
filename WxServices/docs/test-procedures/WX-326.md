# WX-326 Test Procedure — the setup console merges `appsettings.local.json`, it does not rebuild it

**What this verifies:** that re-running `WxServices.Setup` against a box that already has a WxManager
`appsettings.local.json` updates **only** `ConnectionStrings:WeatherData` and leaves every other key
intact — and that an existing file it cannot parse stops the run rather than being overwritten.

**Why a functional run and not only unit tests:** the unit tests pin the generator's input→output
surface, but the defect was never in the generator alone — it was the *composition* (a generator that
knew nothing of the existing file, a plan that never read it, a writer that overwrote unconditionally).
Only an end-to-end re-run exercises that composition against a real file on disk.

**Recording results:** **Test Proc** = `docs/test-procedures/WX-326.md`; **Test Result** =
`PASS yyyy-mm-dd` (setup tooling — it ships in no service binary, so there is no deployed version to
pin). On failure: `FAIL yyyy-mm-dd — <what>`, a ticket comment, and a Bug.

> **Do not edit `appsettings.local.json` while setup is running.** The merged content is prepared before
> the database work and written after it, so an edit made in between is reverted by the write. This is an
> **accepted, documented limitation, not an oversight**: a re-read-immediately-before-write step was built
> to close that window and then removed, because across three review rounds it produced two data-loss
> defects of its own while guarding a window that only opens if you edit this file during your own
> interactive setup run. See `LocalFilesPlan.BuildWxManagerMerged` for the full reasoning.

**Isolation:** every step below runs against **throwaway targets only** — a temp services dir, a temp
install root, and a `WeatherDataTest` / `wxservicestest` pair. The real `C:\HarderWare`,
`services/`, `WeatherData` and `wxservices` are never touched. This is the same isolation
`docs/test-procedures/WX-314.md` §1 establishes; its setup and teardown blocks are reused verbatim
rather than restated, so a change to the isolation strategy has one home.

---

## 0. Unit tests (CI — pure, no DB, no filesystem)

`tests/WxServices.Setup.Tests`. Run (**Windows PowerShell**):

```powershell
dotnet test tests\WxServices.Setup.Tests\WxServices.Setup.Tests.csproj
```

*Expect:* **all green.** The whole `WxServices.Setup.Tests` project must pass — that is the gate, and it
is stated that way on purpose: an enumerated list here is a second copy of the test names that drifts the
moment a test is added, and the first version of this document had already gone stale (it said "the ten
cases" while the code carried more, and listed a renamed pre-existing test among the new ones). Read the
project for the roster; read this for what the roster is *for*:

| Guarantee | Where it is pinned |
|---|---|
| Operator-owned keys survive a re-run, whatever their nesting or type | `LocalJsonGeneratorTests` merge cases |
| A fresh box still gets a connection-string-only file | the `NoExistingFile` / empty-input cases |
| An existing key is updated **in place whatever its case**, never duplicated | `Build_ExistingKeysInAnyCase_…` |
| A file we cannot read or parse aborts and **names the path** | `Build_Unparseable…` / `Build_Unreadable…` |
| The stricter-than-runtime refusal of comments / trailing commas, with a reason | `Build_ExistingFileWithComments…` |
| The remedy note appears only for the cause it explains | `Build_NonJsonSyntaxFailure_OmitsTheCommentsHint` |
| The operator's text comes back byte-identical, not re-escaped | `Build_PreservesNonAsciiAndPunctuation…` |
| The right path is read | `Build_WxManagerFile_ReadsTheWxManagerPath_NotSomeOtherFile` |
| An absent file, a missing InstallRoot, and a BOM'd file are each handled | `RealFilesystemReaderAndWriterTests` |
| Only the WxManager file is replaced atomically — the container files, being single-file bind mounts, are truncated in place | `Build_OnlyTheWxManagerFileIsWrittenAtomically` |
| A failed write leaves the original intact and no temp file behind | `WriteAtomic_FailedWrite_LeavesOriginalIntact_AndRemovesTheTempFile` |

**One guarantee is deliberately absent from that table: *atomicity itself is not unit-tested.*** The row
above claims only what its test can demonstrate — cleanup after a failure. Proving atomicity needs a crash
between truncate and write, which no unit test can stage; it rests on the temp-file-then-`File.Replace`
construction, documented at `WriteAtomic`. An earlier version of this table claimed the stronger guarantee
against a test whose own comment disclaims it, **and named a test that did not exist** — caught by code
review. Stating the gap is worth more than a row that reads as covered.

**Every one of these was confirmed to fail against the un-fixed behaviour** (2026-07-26) — by breaking
the code and watching it go red, not by re-reading the test. A test that has never been seen to fail is
decoration, not coverage.

## 1. Functional isolated-run

Establish the throwaway targets exactly as in `WX-314.md` §1 (temp services dir with the four
`.example` files copied in, temp install root), substituting `wx326` for `wx314` in the two paths.

1. **First run — the fresh-box path still works** (AC-2). Run the console against the isolated set
   per `WX-314.md` §1 step 1, with `--install-root $root --services-dir $svc --database
   WeatherDataTest --sql-login wxservicestest --server .\SQLEXPRESS`.
   - *Expect:* completes; `$root\appsettings.local.json` exists and contains `ConnectionStrings:WeatherData`
     naming `WeatherDataTest` with Trusted auth, and **no** `Fetch:*` / `WxVis:*` keys.

2. **Add operator-owned keys**, standing in for what a real box accumulates:
   ```powershell
   $f = "$root\appsettings.local.json"
   $j = Get-Content $f -Raw | ConvertFrom-Json
   $j | Add-Member -NotePropertyName Fetch -NotePropertyValue ([pscustomobject]@{ HomeIcao = 'KAUS'; RegionSouth = 22 })
   $j | Add-Member -NotePropertyName Claude -NotePropertyValue ([pscustomobject]@{ Model = 'claude-sonnet-4-6' })
   $j | Add-Member -NotePropertyName WxVis -NotePropertyValue ([pscustomobject]@{ MapExtent = 'conus' })
   $j.Fetch | Add-Member -NotePropertyName Locality -NotePropertyValue ([string][char]0x4B + [char]0xF8 + 'benhavn')
   # WriteAllText, NOT `| Set-Content`: PowerShell 5.1's ConvertTo-Json escapes non-ASCII (so the seed
   # would land as København) and Set-Content -Encoding UTF8 adds a BOM. Both are survivable, but
   # they would make the raw-text assertion in step 3 fail for reasons that have nothing to do with the
   # code under test — a false FAIL at the very step added to cover escaping.
   [System.IO.File]::WriteAllText($f, ($j | ConvertTo-Json -Depth 10), (New-Object System.Text.UTF8Encoding $false))
   $raw = Get-Content $f -Raw
   $raw
   ```
   - *Expect:* the file now shows `ConnectionStrings`, `Fetch`, `Claude` and `WxVis`.
   - *Expect (PowerShell 5.1):* the seed file contains the **escaped** form — `$raw` matches
     `København`, **not** the literal `København`. `ConvertTo-Json` escapes non-ASCII on this
     shell. That is expected and harmless: this is only the **seed**, and step 3 asserts on what
     *setup* writes, not on what PowerShell wrote. (Do not "fix" it by hand-editing the file to the
     literal character — either form is a valid input, and the escaped one is the more demanding
     test, since setup must decode it and re-emit the character.)
   - **Why a non-ASCII value is here on purpose:** the merge re-serializes the document, and the
     default JSON encoder would rewrite `ø` as `ø` — semantically identical, visibly not the
     operator's file. Every other value in this procedure is ASCII, so without this one line the
     procedure *cannot detect that class of change at all*. (Found by sibling review, 2026-07-26.)

3. **Re-run setup — the ticket's headline case** (AC-1). Repeat step 1's command.
   - *Expect:* completes without error, and `Get-Content $f -Raw` shows **all four** sections still
     present: `Fetch:HomeIcao` = `KAUS`, `Fetch:RegionSouth` = `22`, `Claude:Model` =
     `claude-sonnet-4-6`, `WxVis:MapExtent` = `conus`, with `ConnectionStrings:WeatherData` present
     and current. **This step is the whole ticket** — before the fix it left `ConnectionStrings` alone.
   - **Assert on the RAW TEXT, not the parsed object:**
     ```powershell
     Get-Content $f -Raw | Select-String -Pattern 'benhavn', '\\u00f8' -AllMatches
     ```
     *Expect:* the literal `København` **matches**, and `ø` does **not**. Reading the file back
     with `ConvertFrom-Json` would resolve `ø` to `ø` and report success either way — a check
     that reads through a normalising layer cannot see normalisation. Same trap as step 4, one level up.

4. **Re-run against a different database — the connection string does move** (the negative control for
   step 3; a merge that silently failed to update anything would also pass step 3). Re-run with
   `--database WeatherDataTest2`, then inspect the file.
   - *Expect:* `ConnectionStrings:WeatherData` now names `WeatherDataTest2`, **and** the four
     operator sections are still intact. Drop `WeatherDataTest2` afterwards.

5. **Malformed existing file aborts before any mutation** (AC-3). Drop the test DB + login (the
   `sqlcmd` block in `WX-314.md` §5a), corrupt the file, and re-run:
   ```powershell
   'this is not json' | Set-Content "$root\appsettings.local.json" -Encoding UTF8
   ```
   - *Expect:* exits non-zero with a message that **names the full path** to the file, says setup will
     not overwrite a file it cannot read, and tells the operator to fix the JSON or move it aside.
     **And** `WeatherDataTest` / `wxservicestest` are both still **absent**, and the corrupted file is
     **byte-for-byte unchanged** — the plan is built before anything mutates, so an unreadable file
     costs nothing but the run.

5a. **A file with comments / trailing commas is refused — loudly, and for a stated reason.** This is a
   deliberate asymmetry, not an oversight: the JSON configuration provider the services and WxManager
   read this file with **accepts** `//` comments and trailing commas (verified 2026-07-26), so the
   content below runs fine in production. Setup still refuses it, because merging means re-serializing
   and `System.Text.Json` cannot round-trip a comment — tolerating it would mean silently deleting the
   operator's annotations, the same data loss as this ticket, only quieter.
   **The here-string terminator `"@` must sit at column 0** — PowerShell 5.1 rejects any leading
   whitespace with *"White space is not allowed before the string terminator"*. It is unindented below
   on purpose; keep it that way if you copy this.
```powershell
$lenient = @"
{
  // the box this was cloned from
  "ConnectionStrings": { "WeatherData": "Server=OLD;" },
  "Fetch": { "HomeIcao": "KAUS" },
}
"@
$lenient | Set-Content "$root\appsettings.local.json" -Encoding UTF8
```
   Re-run step 1's command.
   - *Expect:* exits non-zero; the message names the path **and** explains that comments and trailing
     commas are accepted by the running services but not here, and why. **The file is unchanged.**
   - *Also expect (the point of the asymmetry):* the same content is readable at runtime — confirm with
     `(New-Object Microsoft.Extensions.Configuration.ConfigurationBuilder)` if convenient, or simply
     note that this is asserted by the unit test rather than re-proved by hand here.

6. **Tear down (no residue)** — the `WX-314.md` §6 block, with `$svc`/`$root` pointing at the `wx326`
   paths, plus a `DROP DATABASE WeatherDataTest2` if step 4 left one.
   - *Expect:* the real instance shows **no** `WeatherDataTest` / `WeatherDataTest2` /
     `wxservicestest`, and the real `C:\HarderWare` + `services/` are untouched.

**PASS** = §0 green **and** §1 steps 1–5a meet their Expects with step 6 leaving no residue. Then set
Test Result `PASS <date>` → Done.
