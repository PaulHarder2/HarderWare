# WX-451 — GFS run completeness decided by set membership, not by a count

**Release:** 1.61.3 · **Component:** `WxParser.Svc` (the shared `MetarParser.Data` library changes, so all four services rebuild; the changed path executes only here)
**Verify script:** `docs/test-procedures/WX-451-verify.sh`

---

## Why this needs a functional test at all

The unit tests prove the decision logic — **25 of them, 16 pure and 9 against SQLite in-memory** (measured 2026-08-17). Production is **SQL Server with ~3.3 million rows** in `GfsGrid`, and the EF translation of `Where().Select().Distinct().ToListAsync()` is not the query SQLite ran. The tests prove the intent; only production proves the intent was right.

🔴 **And the failure mode is silent.** If the new evaluation misbehaves against SQL Server, runs are simply never marked `IsComplete`. Consumers — `WxInterp`, `ForecastMapWorker`, `MeteogramWorker` — keep reading the last good run forever, because they are told to select the newest run whose flag is true. **No exception, no error line, model data quietly frozen.** That is the WX-446 shape, which ran 54 hours before anyone noticed.

---

## 🔴 Read this before choosing what to look for

**The obvious signal does not discriminate.** The complete-branch log line is:

```text
NEW   GfsFetcher: run 2026-08-17 18Z marked complete (121/121 hours stored).
OLD   GfsFetcher: run 2026-08-17 18Z marked complete (121/121 hours stored).
```

**Byte-identical for a healthy run.** The old code printed `{storedHourCount}/{expectedHours}`, which is also `121/121` when nothing is missing. Anyone verifying this change by looking for "marked complete" would be running an unfailable check — it passes against the unfixed code.

✅ **The discriminating signal is the `missing` clause in the INCOMPLETE branch:**

```text
NEW   ...is 41/121 hours complete — missing f041-f120 — will resume next cycle.
OLD   ...is 41/121 hours complete — will resume next cycle.
```

The old code had **no missing-hours list at all**, so this string can only come from 1.61.3+. It appears on every cycle while a run is still downloading.

---

## ⚠️ Timing — expect WAIT for hours after the deploy

`FetchAndInsertAsync` **returns early** on a run already marked complete, so the new code does not run for it. The first genuine exercise is the **next GFS cycle**, which is not fetchable until ~3.5 hours after its nominal time (00/06/12/18Z), then needs its download window.

**So a WAIT immediately after deployment is expected and correct, not a fault.**

## Steps

### 1. Confirm the release is deployed

```bash
bash docs/test-procedures/WX-451-verify.sh
```

**Expect:** either a `WAIT` naming 1.61.3 as not yet in `deploy-history.log` (deploy first), or the full report. The script resolves its own deploy boundary; do not pass `--since` for a real verification.

### 2. Wait for the next GFS cycle, then re-run

**Expect:** `...carrying the missing-hours clause:` **greater than 0**.

That number is the whole test — it proves the set-membership code executed against the real database. If it is 0 and a cycle has completed since the deploy, that is **not** a pass; read step 4.

### 3. Read the regression signatures

**Expect both zero:**

| signature | meaning if non-zero |
|---|---|
| `negative MaxForecastHours ERROR` | `Gfs:MaxForecastHours` is misconfigured. Correct it; while it holds, **no run can ever be marked complete**. Logged once per process, so 1 is a standing condition rather than a blip. |
| `runs fully stored but NOT marked complete` | 🔴 **The silent-freeze symptom.** A run holds every expected hour and the flag is still 0. ⚠️ A same-cycle transient is possible — the fetch stores the last hour and marks the run in one cycle — so **re-run the script before treating it as real.** Non-zero on two consecutive runs is a FAIL. |

⚠️ **If that second row shows `?` rather than a number, the database check did not run — and the script will report `WAIT`, never `PASS`.** The DB check is the only detector for the silent-freeze signature, so a verdict without it would certify the one thing this ticket exists to catch as unexamined. Re-run somewhere `powershell.exe` and `SQLCMD.EXE` are both reachable.

> ⚠️ **This paragraph said a PASS in that state "attests the log signal only" until 2026-08-17.** That was true of the first cut of the script and was made false by the same commit that wired the DB check into `vl_verdict`'s precondition slot — which did not sweep this sentence. It told an operator to accept a PASS on exactly the partial evidence the fix had made unreachable. *(Review round 2, finding 6.)*

**The one exception, and it is deliberate:** a **negative `Gfs:MaxForecastHours`** is a log-only signature needing no database at all. When that fires, the verdict is `FAIL` even with the DB check unavailable — because the failure is already conclusive. Reporting it as `WAIT` would have made the pasted Jira artifact say the opposite of what was measured *(finding 7)*.

### 4. If the missing-hours clause never appears

Distinguish three causes before concluding anything:

1. **No run has been incomplete since the deploy.** If a cycle completed entirely within one fetch pass, the incomplete branch never logged. Check `runs marked complete` — if it rose, the code ran but only through the non-discriminating branch. **Wait for the next cycle rather than declaring a fault.**

   ⚠️ **That row counts only the real completion line, and the distinction matters.** `FetchAndInsertAsync` also logs *"is already marked complete — skipping"* on its early return, which contains the same words and is emitted **precisely when the completeness code does not run** — and on the live log the skip line **outnumbers real completions by roughly five to one**. The script therefore anchors on `marked complete \(` — the opening parenthesis of `(121/121 hours stored)`. **If you count these by hand, use that anchor**, or the number rises fastest when nothing under test executed.

   The invariant to re-check, rather than counts that go stale as the log grows:

   ```bash
   # Derive the log path from the DEPLOYED InstallRoot rather than hardcoding a mount path.
   # Run from anywhere in the repo; WXS is the WxServices directory.
   WXS=$(git rev-parse --show-toplevel)/WxServices
   ROOT=$(jq -r '.InstallRoot' "$WXS/appsettings.shared.json")          # e.g. C:\HarderWare
   LOG="$(printf '%s' "$ROOT" | sed 's|^\([A-Za-z]\):|/mnt/\l\1|; s|\\|/|g')/Logs/wxparser-svc.log"
   [ -r "$LOG" ] || { echo "CANNOT READ $LOG -- this is NOT a result, fix the path"; exit 1; }
   skip=$(grep -Fc 'already marked complete' "$LOG")
   real=$(grep -Fc 'marked complete ('       "$LOG")
   total=$(grep -Fc 'marked complete'        "$LOG")
   other=$(( total - skip - real ))
   if (( other == 0 )); then
     echo "OK: $skip skip + $real real == $total total"
   else
     echo "RESIDUE: $other line(s) contain 'marked complete' but match neither anchor --"
     grep -F 'marked complete' "$LOG" | grep -Fv 'already marked complete' \
       | grep -Fv 'marked complete (' | cut -c1-100 | head -3
   fi
   ```

   ⚠️ **ONE ASSUMPTION SURVIVES THE DERIVATION AND IS STATED RATHER THAN HIDDEN: the WSL
   `/mnt/<drive>` mount convention.** `InstallRoot` is a *Windows* path (`C:\HarderWare`), so reading
   it from WSL requires translating the drive letter — the `sed` above does that and the readability
   guard catches it if the mount differs. Verified 2026-08-17: the derivation reproduces
   `/mnt/c/HarderWare/Logs/wxparser-svc.log` exactly, and a control root of `D:\Elsewhere` correctly
   yields `/mnt/d/Elsewhere`, so it responds to the value rather than returning a constant.

   ⚠️ **THE SAME HARDCODING EXISTS IN THE SCRIPTS AND IS DELIBERATELY NOT CHANGED HERE.** All four
   `*-verify.sh` files and `verify-lib.sh`'s own three defaults hardcode `/mnt/c/HarderWare/Logs/`.
   That is a house pattern across shared verification machinery, so changing it on this ticket would
   leave one document disagreeing with five files. Worth its own ticket; noted, not folded in.
   *(CodeRabbit, PR #227 — raised against this block, and correct about the class.)*

   🔴 **THE READABILITY GUARD AND THE RESIDUE BRANCH ARE BOTH LOAD-BEARING; THE PREVIOUS VERSION HAD
   NEITHER AND COULD NOT FAIL.** With `$LOG` missing, all three `grep -Fc` calls return **empty**,
   bash coerces empty to 0 in `(( ))`, and `0 == 0` printed **OK against a log that does not
   exist** — measured. And a bare equality cannot say *what* the residue is.

   🔴 **WORSE, THE OLD FORM BROKE PRECISELY IN THE FAILURE CASE IT SHOULD SURVIVE.** The
   negative-bound ERROR reads *"…no run **will be marked complete** until this setting is
   corrected"* — our own message — so `total` counts it while neither anchor does. Measured on a log
   holding just that line: `0 + 0 != 1`. **The invariant failed exactly when the misconfiguration
   this ticket cares about was present.** The residue branch now prints the offending line instead,
   which is useful rather than merely correct. *(CodeRabbit, PR #227.)*

   ⚠️ **`-F` (fixed string), not an escape — because the escape is dialect-dependent and inverts.**
   In **ERE** (`grep -E`, which the verify script's `cnt` uses) a bare `(` opens a group, so `\(` is
   required. In **BRE** (plain `grep`) it is the reverse: `\(` *opens* a group and fails with
   `Unmatched ( or \(`. This invariant previously carried the ERE form while telling you to run BRE,
   so it aborted rather than counting — the round-1 bug exactly inverted. `-F` disables regex
   entirely and is right in every dialect, including the harness's ugrep shim. *(CodeRabbit, PR #227.)*

   ⚠️ *This paragraph carried `295 skip / 54 real` until 2026-08-17. Review round 2 corrected exactly that arithmetic **in the verify script and not here** — the fix landing in one of two restatements, which is this estate's most-repeated defect and which it had just been found for. Stating the invariant removes the restatement rather than re-synchronising it.*
2. **The service is not on 1.61.3.** Check the deploy boundary line in the header.
3. **The evaluation is broken.** Then `runs fully stored but NOT marked complete` will be non-zero, which is the FAIL in step 3.

## Manual spot-check (optional, and the strongest evidence available)

🔴 **THIS QUERY MUST BE A SET TEST, NOT A COUNT — and until 2026-08-17 it was a count, which is the exact defect WX-451 fixes.** It read `COUNT(DISTINCT g.ForecastHour) … = 121` with **no range filter**, so a run missing `f113` while holding `f200` returned **121** and read as healthy. Measured side by side on the live server against exactly that synthetic run:

```text
OldCheck_DistinctHours   New_MissingCount   New_OutOfRangeCount
         121                     1                   1
```

**The old form could therefore accept a count-based implementation as proof that the count-based implementation was gone.** It sat under a heading calling it *"the strongest evidence available"*. *(CodeRabbit, PR #227, rated Major — and neither `/code-review` round found it.)*

Set `@MaxFH` from the **effective** `Gfs:MaxForecastHours` — the verify script prints which config layer supplied it. Do not assume 120.

```sql
SET NOCOUNT ON;
DECLARE @MaxFH int = 120;   -- ← the EFFECTIVE bound; see the verify script's "supplied by layer"

-- 🔴 GUARD FIRST. Without it a negative bound makes TOP(@MaxFH + 1) into TOP(0): the expected set
-- is EMPTY, so MissingCount is 0 for EVERY run and the query reports a frozen system as healthy.
-- Measured: @MaxFH = -1 -> ExpectedRows 0, MissingCount 0. That is an unfailable check inside the
-- query written to replace one. Values below -1 error instead. (CodeRabbit, PR #227.)
IF @MaxFH < 0
    SELECT 'NOT EVALUATED - Gfs:MaxForecastHours is negative; no run can be marked complete until it is corrected.' AS Status;
ELSE
WITH expected AS (
    SELECT TOP (@MaxFH + 1)
           ROW_NUMBER() OVER (ORDER BY (SELECT NULL)) - 1 AS ForecastHour
    FROM sys.all_objects
)
SELECT r.ModelRunUtc, r.IsComplete,
       (SELECT COUNT(*) FROM expected e
         WHERE NOT EXISTS (SELECT 1 FROM GfsGrid g
                            WHERE g.ModelRunUtc = r.ModelRunUtc
                              AND g.ForecastHour = e.ForecastHour))   AS MissingCount,
       (SELECT COUNT(DISTINCT g2.ForecastHour) FROM GfsGrid g2
         WHERE g2.ModelRunUtc = r.ModelRunUtc
           AND (g2.ForecastHour < 0 OR g2.ForecastHour > @MaxFH))     AS OutOfRangeCount
FROM GfsModelRuns r
ORDER BY r.ModelRunUtc DESC;
```

**Expect:** the newest complete run shows `IsComplete = 1` and `MissingCount = 0`.

⚠️ **`OutOfRangeCount` is expected to be 0 in normal operation and is NOT a failure on its own.**
The implementation marks a run complete when every hour in the *current* range is present, whatever
surplus it also holds — and logs the out-of-range note in that case. So a legitimately complete run
can carry `OutOfRangeCount > 0`. *(An earlier draft demanded 0 and contradicted its own table row
below — CodeRabbit, PR #227.)*

🔴 **BUT IT PROVES ONLY THAT ROWS EXIST OUTSIDE THE CURRENT EFFECTIVE RANGE — IT DOES NOT PROVE A
HORIZON REDUCTION.** That is one hypothesis among several: a bad insert, a partial migration, or a
bug could produce identical rows. **Confirm the reduction independently** — the bound's current value
and supplying layer (the verify script prints both), plus `deploy-history.log` or the config history
showing when it changed — **before** treating the surplus as expected orphan data. Unconfirmed,
treat it as unexplained and investigate. *A hypothesis that explains the evidence is not a
diagnosis.*

| what you see | what it means |
|---|---|
| `MissingCount = 0` and `IsComplete = 0`, persisting | 🔴 the silent-freeze failure this ticket exists to prevent |
| `MissingCount > 0` and `IsComplete = 1` | 🔴 completeness is still being decided by a count — the WX-451 defect itself |
| `OutOfRangeCount > 0` | ⚠️ rows exist outside the current range — **cause NOT established.** A horizon reduction is one hypothesis; a bad insert, a partial migration or a bug produce identical rows. **Confirm from config/deploy history before calling it expected** (see the qualification above). |
