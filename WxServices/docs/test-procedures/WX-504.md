# WX-504 — Functional test procedure (production §13 watch)

**Ticket:** WX-504 (Bug under Epic WX-137). The fix-forward for WX-340's FAIL: the reconciler's user
message now carries `block_local_labels`, giving every forecast block its local date, weekday,
day-part and clock span. The prompt's day-part and window rules take their times from it, and the
prompt no longer models storm wording.

**Release under test:** v1.61.4 · **Component:** `WxReport.Svc` (the reconciler).

## Why this is a production watch

The fix changes what the model is given and told. A stubbed-Claude unit test cannot show that the
model now writes correct prose, so the evidence is the prose that actually ships. The unit tests
cover only the deterministic half: the labels are right, including across DST, and they reach the
user message. The planned pre-deploy harness comparison could not run on PaulOmniBook (Windows Smart
App Control blocks the harness's build output; WX-504 comment 15882), so this watch is the only
measure of the fix.

## The classes

Judged against the reconciled snapshot the report was built from, in the locality's local time.

| Class | A defect is |
|---|---|
| **C1** — precipitation at a dry time | prose places rain, snow or a storm in a block, day-part or day whose blocks are all dry. Includes a 00:00–06:00 block called "morning", and a window named a day early or late. |
| **C2** — an aggregate period called dry | "the weekend", "the week" or "the next few days" called dry, clear or quiet while a day within that period has precipitation. **C2h** is the same claim hedged ("mostly dry"); record it separately, because whether it counts is a ruling, not a measurement. |
| **C3** — storm wording without a severe block | a storm-family word ("storm", "thunderstorm", "thunder", "squall", "storm energy", "convective signal", or any-language equivalent) used about a window with no `severeFlag`. **C3p** is such a word used only about the PRIOR or removed forecast; record it separately. |
| **C4** — a midnight-crossing window named by its tail | a change window spanning two local dates described by its second date only. Recorded; not part of the verdict (WX-504 AC-6). |

## Files beside this procedure

* `WX-504-dump.ps1` — writes every sent `CommittedSend` since `-Since`, joined to its snapshot,
  language and locality timezone, as UTF-8 JSON lines. It **reads the production database**.
* `WX-504-screen.py` — screens the dump for candidates in every class. **A screen, not a verdict**:
  most hits are false positives, and every hit is judged by hand. `--selftest` must pass first.
* `WX-504-harness-to-rows.py` — converts QA-harness `--raw` output into the screen's input. Only
  used if the harness can run (see *Why this is a production watch*).

## Procedure

1. **Confirm the deploy.** In `deploy-history.log`, find the most recent `WxReportSvc` line at
   version `1.61.4` (the log writes the component without a dot). *Expect:* one line. Its
   timestamp is the window start, `SINCE`.

2. **Baseline smoke.** Confirm that `WxReport.Svc` came up cleanly: the container is healthy, sends
   continue, and there are no new ERRORs in `wxreport-svc.log` beyond the pre-deploy background.
   *Expect:* healthy.

3. **Wait for the window.** At least **14 days** after `SINCE`. Step 6 then checks that the window
   actually tempted each class, because a class cannot fail on reports that never tempt it.

4. **Dump the corpus.** The session running this procedure is blocked from production reads, so
   Paul runs this line himself in the terminal, with `!` prefixed and `SINCE` filled in:

       powershell.exe -NoProfile -ExecutionPolicy Bypass -File "$(wslpath -w /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-504-dump.ps1)" -Since 'SINCE' -OutPath "$(wslpath -w /tmp)\wx504-corpus.jsonl"

   *Expect:* `rows=N`, where N > 0.

5. **Self-test the screen.**

       python3 /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-504-screen.py --selftest

   *Expect:* every line `ok`, and a final line `65/65 as expected`. Any `FAIL` means the screen is
   broken; stop.

6. **Screen the corpus.**

       python3 /mnt/c/Code/HarderWare/WxServices/docs/test-procedures/WX-504-screen.py /tmp/wx504-corpus.jsonl

   *Expect:* a line `rows=N  unique (snapshot,lang,prose)=M  skipped={…}`, an `exposure` line,
   counts per class and language, then a `sample` line giving how many reports per language were
   drawn for step 8.
   The candidates are written to `/tmp/wx504-corpus.jsonl.candidates.json` and the sample to
   `/tmp/wx504-corpus.jsonl.sample.json`.
   * **Exposure.** Each of `nonsevere_storm` (a non-severe thunderstorm block), `early_only_rain`
     (rain in 00:00–06:00 with a dry morning after it), `midnight_wet_window` (a wet evening into a
     wet next early-hours block) and `partly_wet_weekend` must be above 0. If any is 0, the window
     never tempted that class: wait longer and redo from step 4. Record no verdict.
   * **Skipped rows.** A non-empty `skipped` names rows the screen could not read, such as a
     language it has no word lists for. Read every such report in full by hand and judge it for
     classes 1–3 in step 7, or record no verdict.

7. **Judge every C1, C2 and C3 candidate by hand** against the report's own snapshot, in local time:
   the dump's `SnapshotBody`, in the row's `LocalityTz`. If that is empty, use `LocalityTz` from another
   row with the same `ForecastSnapshotId`, then the row's own `RecipientTz`, which is the order the
   screen uses. For each one, record: send id, date, class,
   the offending sentence, and the grid blocks it contradicts, or the reason it is a false positive.
   *Expect:* a written disposition for every candidate.

8. **Hand-read the sample.** The screen matches phrases, so it can miss a defect worded in a way it
   does not recognise, and a missed report is never judged. The sample file holds up to 10 reports
   per language that the screen did **not** flag, chosen by a fixed seed. Read each one in full
   against its own snapshot, exactly as in step 7, for classes 1–3. A confirmed instance counts in
   the verdict like any other; record the phrase the screen missed as well.
   *Expect:* a written note for every sampled report, "clean" or a confirmed instance.

9. **Cross-check one confirmed instance per class** (if any) against the report's rendered
   `EmailBody`, a column the dump carries, to confirm the prose reached the recipient in that form.

## Verdict

* **PASS** — every step 6 exposure count is above 0, every skipped row was judged by hand, every
  sampled report was read, and no confirmed C1, C2 or C3 instance reached a recipient.
  Record `PASS yyyy-mm-dd @ v1.61.4` in the ticket's **Test Result**, with the C4, C2h and C3p
  counts in a ticket comment.
* **FAIL** — any confirmed C1, C2 or C3 instance. Record `FAIL yyyy-mm-dd @ v1.61.4`, the offending
  sentences, and the class counts before and after, compared with WX-340 comment 15878.

## Resume-queue registration (WORKFLOW §8)

* **(a) Jira issue:** WX-504.
* **(b) Watcher identity and output:** a manual, periodic read using the three files above; nothing
  runs automatically.
* **(c) End trigger:** 14 days after the deploy → run steps 4–9. If step 6 shows any exposure count
  of 0, wait longer and repeat; otherwise record the verdict.
* **(d) How to know it is still running:** it is not an automated sensor. Its liveness signal is the
  resume-queue entry. If the entry is cleared without a recorded verdict, that is the defect to catch.
