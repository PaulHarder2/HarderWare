# WX-446 — Manual test procedure

**Ticket:** WX-446 — TAF ingestion has been dead since 2026-08-14; `aviationweather.gov` rejects the
`hours` parameter on its TAF endpoint while still requiring it on METAR.
**Component:** `WxParser.Svc` (containerised). **Run on PaulOmniBook**, after the release is deployed.
**Prerequisite:** `SQLCMD.EXE` and the `WeatherData` database reachable; Docker Desktop running.

**What changed:** `&hours=24` removed from **four** TAF request sites — `TafFetcher.cs` ×3 (bbox,
single-`ids`, and the chunked WX-140 `ids` path) and `AirportLocator.cs` ×1 (the `format=json` TAF
lookup). **METAR's five `hours=` usages are untouched, deliberately** — that asymmetry is the bug.

🔑 **The measure that matters is the DATA, not the log.** This outage produced 338 error lines and ran
30 hours; what nobody was told is that we had zero valid TAFs. So step 1 is a row count, not a grep.

## Steps

1. **Live TAF coverage — the acceptance measure (AC-2).**

   ```bash
   powershell.exe -NoProfile -Command "& 'C:\Program Files\Microsoft SQL Server\Client SDK\ODBC\170\Tools\Binn\SQLCMD.EXE' -E -C -S localhost\SQLEXPRESS -d WeatherData -h -1 -W -Q \"SET NOCOUNT ON; SELECT 'live_tafs=' + CAST(COUNT(*) AS varchar(20)) + ' stations=' + CAST(COUNT(DISTINCT StationIcao) AS varchar(20)) FROM Tafs WHERE ValidFromUtc<=GETUTCDATE() AND ValidToUtc>=GETUTCDATE(); SELECT 'newest_received=' + CONVERT(varchar(30),MAX(ReceivedUtc),126) FROM Tafs;\""
   ```

   *Expect:* `live_tafs` **non-zero and near 399 stations**, and `newest_received` **after the deploy
   time**. It was `live_tafs=0`, `newest_received=2026-08-14T15:48:15` before the fix.
   ⚠️ **The station count is load-bearing, not decoration.** A single inserted row would make the
   count non-zero while the bbox fetch was still failing; ~399 is what says the bulk path works.

2. **METAR is unaffected — the negative control (AC-3).** Same command, `Metars` and `ObservationUtc`:

   ```bash
   powershell.exe -NoProfile -Command "& 'C:\Program Files\Microsoft SQL Server\Client SDK\ODBC\170\Tools\Binn\SQLCMD.EXE' -E -C -S localhost\SQLEXPRESS -d WeatherData -h -1 -W -Q \"SET NOCOUNT ON; SELECT 'metar_newest=' + CONVERT(varchar(30),MAX(ObservationUtc),126) + ' metar_received=' + CONVERT(varchar(30),MAX(ReceivedUtc),126) + ' utcnow=' + CONVERT(varchar(30),GETUTCDATE(),126) FROM Metars;\""
   ```

   *Expect:* **`metar_received` after the deploy time**, and `metar_newest` within a few minutes of
   `utcnow`. **This is the control against a fix that over-reached** — if `hours` had been stripped
   from METAR too, this is what would show it.
   🔴 **`metar_received` is the load-bearing half, and an earlier draft had only `metar_newest`.**
   `MAX(ObservationUtc)` is satisfied by rows ingested *before* the deploy, so a METAR path broken by
   this change — 400s, zero inserts — would still show a recent observation time for several minutes
   and **PASS**. `ReceivedUtc` is when *we* wrote the row, so it is the only one that moves when
   ingestion is alive.

3. **The fetch actually succeeded, rather than the rows being stale survivors (AC-1).**

   ```bash
   grep -aE 'TAF (fetch failed|fetch done|No TAF reports|No TAFs parsed)|Database error during TAF' \
     /mnt/c/HarderWare/Logs/wxparser-svc.log | tail -50
   ```

   *Expect:* at least one `TAF fetch done. Inserted: N` **after the deploy**, and **no** new
   `TAF fetch failed`.
   ⚠️ **Read the log FILE, not `docker logs`.** log4net writes to disk; the container's stdout carries
   **zero** TAF lines — measured 2026-08-16, `docker logs --since 12h services-wxparser-1 | grep -ic taf`
   returned **0** while the file held the failures. A `docker logs` grep here returns nothing and looks
   exactly like "no failures".
   ⚠️ **`grep -a`**, because the log contains bytes `grep` may treat as binary and silently skip.
   🔴 **`tail -50`, not `tail -5`, and the pattern is wider than "failed" — both because "no new
   failures" is a UNIVERSAL NEGATIVE and a truncated window makes it trivially true.** One cycle emits
   a line per seed box *and* one per `ids=` chunk, so a single early bbox failure is pushed out of a
   5-line window by later successes and the step reads clean. A failed bbox returns count 0 so
   `FetchSplitAsync` does not split — it emits exactly **one** line, the easiest possible one to bury.
   The pattern also now catches the three silent-failure logs a "failed"-only grep misses:
   `No TAF reports were returned for:`, `No TAFs parsed successfully`, and
   `Database error during TAF batch insert` — an HTTP 200 with an empty body hits the first of those
   and is otherwise invisible while the `ids=` chunks satisfy the positive half.
   ⚠️ **The cycle runs about every 10 minutes** (measured: 21:14:34, 21:24:36 on 2026-08-16), so if no
   cycle has run since the deploy this is **BLOCKED, not FAIL** — wait for the next one.

4. **`AirportLocator` TAF lookup — the fourth changed call site (AC-7).**

   The other three steps read the `Tafs` table and `wxparser-svc.log`; **this site touches neither.**
   `AirportLocator.cs:204` is reached only from `WxReport.Svc/RecipientResolver`, and only when a
   recipient has coordinates and **`TafIcao IS NULL`** — the gate at `RecipientResolver.cs:153`.
   Locality members skip the lookup entirely.

   ```bash
   powershell.exe -NoProfile -Command "& 'C:\Program Files\Microsoft SQL Server\Client SDK\ODBC\170\Tools\Binn\SQLCMD.EXE' -E -C -S localhost\SQLEXPRESS -d WeatherData -h -1 -W -Q \"SET NOCOUNT ON; SELECT 'reachable=' + CAST(COUNT(*) AS varchar(10)) FROM Recipients WHERE TafIcao IS NULL AND LocalityId IS NULL AND ((Latitude IS NOT NULL AND Longitude IS NOT NULL) OR (Address IS NOT NULL AND LTRIM(RTRIM(Address)) <> '')); SELECT 'diagnostic_localities_null=' + CAST(SUM(CASE WHEN TafIcao IS NULL THEN 1 ELSE 0 END) AS varchar(10)) FROM Localities;\""
   ```

   *Expect, when a reachable recipient exists:* isolate the **post-deploy** cycle and read the
   resolver's own four messages —

   ```bash
   awk '/Starting report cycle\./{buf=""} {buf=buf $0 ORS} /Report cycle complete\./{last=buf} END{printf "%s", last}' \
     /mnt/c/HarderWare/Logs/wxreport-svc.log |
     grep -aE 'nearest TAF = |no TAF station found|Nearest TAF station lookup failed|No TAF stations found near'
   ```

   *Expect:* `nearest TAF = <ICAO>`, and **none** of `no TAF station found`,
   `Nearest TAF station lookup failed`, `No TAF stations found near`.
   🔴 **`tail -3` was wrong and is replaced.** It can select a **pre-deployment** entry, so it proves
   nothing about the current cycle — the same truncated-window defect as step 3's original `tail -5`,
   committed again one step later. Isolating between `Starting report cycle.` and
   `Report cycle complete.` binds the check to one cycle; confirm that cycle began after the deploy.

   🔴 **Expect, today: BLOCKED.** Measured 2026-08-16, immediately before this change landed —
   `reachable=0`, `diagnostic_localities_null=0` — **re-run verbatim against the rewritten query at 2026-08-16 22:4xZ, not relabelled from the earlier one.** **Nothing can trigger the lookup**, so this step is
   unrunnable without writing a null into production data, which this ticket will not do to satisfy
   its own test. **Record `BLOCKED — AC-7 not evaluated`, never PASS.**
   ⚠️ **Re-run the count before recording that** — it is a measurement, not a standing fact, and a
   recipient added since would make the step runnable.

## Verdict

- **PASS** — record `PASS yyyy-mm-dd @ <version>` in **Test Result**.
- **FAIL** — record the failed step(s) and what was observed.
- **BLOCKED — record `BLOCKED — AC-n not evaluated`, never PASS or FAIL.** Reachable here: the release
  is not deployed yet, no TAF cycle has run since the deploy, or SQL/Docker is unreachable. **A check
  that could not run is not a check that passed.**

## 🔴 A LATENT DATA HAZARD THIS FIX DOES NOT HEAL — measured, and currently harmless

`RecipientResolver` gates its lookup on `if (recipient.TafIcao is null)`, and when
`FindNearestTafStationAsync` returns null it persists the sentinel **`"NONE"`**. `"NONE"` is not null,
**so the lookup is never re-attempted.** During the outage every call returned null (400 → exception →
`return null`), so any recipient or locality **first resolved between 2026-08-14 15:59Z and this
deploy** would be permanently stamped and would never receive a TAF forecast again — even with
ingestion healthy.

**Measured 2026-08-16, immediately before this change landed:**

```text
Recipients  TafIcao='NONE'   0 of 11
Localities  TafIcao='NONE'   0 of 4
```

✅ **So the hazard is LATENT, not live** — nothing was first-resolved during the window, and there is
no damage to repair today. It is recorded here rather than fixed because the repair
(`UPDATE … SET TafIcao = NULL WHERE TafIcao = 'NONE'`, plus a gate that distinguishes *"looked and
found nothing"* from *"could not look"*) is a behaviour change well outside "tiny edits", and would
be a no-op against the measured zero.
⚠️ **Re-run those two counts before assuming it stayed zero.** The window closes at deploy, but any
recipient added between this measurement and the deploy lands in it.
