## TL;DR

Three new Claude models shipped in September (Opus 5.5, Sonnet 5.5, Fable 5.1); the Opus adoption trigger fires on Opus 5.5, which is 20% cheaper and is Anthropic's new recommended default for Opus-tier work. ## Actionable Findings

### 1. Claude Opus 5.5 (September 22) — Adoption Trigger Fires; Verify/Update Claude Code

**What changed.** `claude-opus-5-5` released September 22, 2026 at $4/$20 per MTok — 20% cheaper than Opus 5 ($5/$25), same 1M context window, same description ("for long-running agentic coding and knowledge work"). The models overview now says "start with Claude Opus 5.5 for most workloads." Four breaking changes vs Opus 5 are listed, but none affect using Claude Code as an interactive coding assistant: they target code that explicitly sets `thinking: {"type": "disabled"}`, uses `tool_choice: "any"/"tool"`, uses the `computer_20251124` tool on the Claude API, or streams inter-tool text.

**Why it matters.** The Opus adoption entry's trigger has fired: `claude-opus-5-5` is not in the evaluated set, and it is the new recommended Opus-tier model at a lower price. **Verdict for Claude Code: adopt Opus 5.5.** The Fable 5.1 check (finding 2) declines by the same cost argument. Whether Claude Code has already adopted Opus 5.5 as its default cannot be verified from the repo — the same blind spot the August 2026 Opus 5 finding hit. Add `claude-opus-5-5` to the evaluated set whether or not it is already in use.

**Cost to add.** ~20% savings on Claude Code token spend if not already on Opus 5.5; free if the CLI already defaults to it.

**Recommended next step.** In a live Claude Code session, ask it to report its model. `claude-opus-5-5` means already done; any earlier model ID means update the config. A reported `claude-opus-5[1m]` or older is the signal to act.

**Sources.**

- https://platform.claude.com/docs/en/about-claude/models/overview

### 3. WxServices Migration Scope Correction — Forced Tool Use Also Breaks on Sonnet 5.5

**What changed.** The Sonnet 5.5 spec explicitly states "Setting `temperature`, `top_p`, or `top_k` to a non-default value returns a 400 error" and "Forced tool use returns an error" (`tool_choice: {"type": "any"}` or `{"type": "tool"}`). The Sonnet 5 deferred entry documents the migration work as removing `temperature` from "lines 213 and 405." Both claims are now stale: the current code (verified) sends `temperature` at lines **218, 271, and 458**, and sends `tool_choice: {"type": "tool"}` at lines **284 and 471**. Forced tool_choice was NOT broken on Sonnet 5; it IS broken on Sonnet 5.5. No deferral trigger has fired — the 2026-12-01 backstop is the nearest — but the scope is larger than the deferred entry records.

**Cost to add.** Extra migration work: two forced-tool-choice call sites to replace with `tool_choice: "auto"` plus strict tool use; validate output shape is preserved.

**Recommended next step.** Before the December working session: read the Sonnet 5.5 migration guide's forced-tool-use section, and confirm that `strict: true` on `tool_choice: "auto"` preserves the structured-output contract for the reconciler and translator. The current call sites are temperature at lines 218/271/458 and forced tool_choice at 284/471.

**Sources.**
- https://platform.claude.com/docs/en/models/sonnet-5-5/overview
